# TGFX AOT 可安全分解子集规范

本文定义 TGFX 预编译着色（AOT）能力当前可以安全服务的效果组合集合：支持哪些形状、不支持哪些形状、判定依据是什么、接入方如何自查与调整。读者不需要了解 TGFX 内部实现，只需要具备图形开发的一般概念。

## 1. AOT 交付的是一个可证明安全的绘制子集，而不是全量绘制能力

AOT 的价值命题是：把"哪些绘制永远不需要运行时编译"变成一个可以枚举、可以验证、可以写进合同的清单。清单内的组合由构建期产物直接服务，清单外的组合仍由运行时编译服务，两者的边界由库在每一次绘制时确定性地判定，不由接入方猜测。

### 1.1 全部术语限定在读者已有的图形概念之内

| 术语 | 含义 |
| --- | --- |
| AOT（构建期预编译） | 在库发布之前，把一组绘制组合对应的 Shader 全部编译成目标后端的产物，随库一起分发。 |
| JIT（运行时编译） | 在设备上首次遇到某个绘制组合时，临时生成并编译 Shader。首次出现有一次性卡顿与驱动编译成本。 |
| VS / FS | 顶点 Shader 与片元 Shader。一次绘制各需要一份，两者配对后才构成可用程序。 |
| Pipeline（渲染管线） | VS、FS 加上混合、深度等固定状态的整体，是 GPU 上真正被执行的对象。 |
| Bundle（预编译包） | 全部预编译 Pipeline 的打包文件，按后端各一份，随库分发，构成包体增量。 |
| Program Key（程序键） | 一次绘制所需程序的唯一标识，由绘制特征决定。例：同一份纹理填充逻辑，"带设备遮罩"与"不带遮罩"是两个不同的 Program Key，对应两条不同的 Pipeline。 |
| Stage asset key（阶段资产键） | Program Key 内部对 VS、FS 两份资产的索引。两个阶段独立编号，同一个 FS 资产可以被多个 Program Key 复用。 |
| 一次绘制 | 一次 `drawImage`、`drawRect`、`drawTextBlob` 等调用落到 GPU 上的最小单位。AOT 的命中判定按此粒度进行，与画面、图层无关。 |
| 单 Pass / 多 Pass | 单 Pass：一次绘制在一个渲染批次内完成。多 Pass：需要先把中间结果画到一张中间纹理，再用它继续绘制。每多一个 Pass 就多一张中间纹理的显存与带宽成本。 |
| 中间纹理 | 多 Pass 之间传递结果的临时纹理，通常 RGBA8 格式。 |

### 1.2 子集边界的判定按单次绘制进行，命中与未命中都是确定行为

- 同一行代码可以命中也可以未命中，取决于运行时参数。例：同一个 `drawImage`，图片是普通 RGBA 纹理时命中预编译程序；图片来自 YUV 视频帧时走另一条专用路径；两者都是确定行为。
- 未命中不等于错误，只表示这次绘制由运行时编译服务，首帧有一次性编译成本，随后被设备缓存。
- 清单只增不减：任何已支持的组合不会因为版本升级而退出子集；退出子集的唯一方式是绘制特征本身发生了变化。

## 2. 一个效果组合可安全分解，当且仅当三个条件同时成立

三个条件缺一不可；第 3 节列出的每个已支持形状都能逐条对上这三个条件，第 4 节列出的每个不支持形状都至少违反一条。

### 2.1 结构可分解：效果的计算图必须能拆成"每个输出像素只依赖同一坐标输入"的片段

一个像素的颜色只由同一位置的输入纹理像素、几何颜色和常量参数决定时，这段计算可以原样搬进一个融合 Shader。

- 反例：`ImageFilter::Blur` 的每个输出像素需要读取周围半径内的几十个输入像素，输出与输入不再是同一坐标的映射，无法搬进逐像素融合 Shader。

### 2.2 中间结果可传递：拆出的各段之间只通过寄存器传值，不经过中间纹理

单 Pass 内各段计算的中间结果保留在 GPU 寄存器里，精度不损失；一旦需要写入中间纹理再读回，就引入了 RGBA8 量化和一次额外的 Pass。

- 反例：先模糊再调色的滤镜序列，模糊的结果必须落到一张中间纹理才能被调色读取，两段之间无法只用寄存器传值，因此不能自动合成一个单 Pass 程序。

### 2.3 子图可预编译：拆出的每一段必须在构建期就能枚举出全部参数形状

构建期必须能把这一段的所有可能形态写成有限个程序变体；参数值可以运行时再传，参数的形状（有几个纹理、有没有遮罩、用哪类操作）必须提前确定。

- 反例：`RuntimeEffect` 允许接入方传入任意 Shader 源码，构建期无法预知其形态，任何包含它的组合都无法预编译。

## 3. 已支持的形状可以完整枚举，不在枚举内即不受支持

### 3.1 单纹理加线性串联的一元颜色链在单个 Pass 内完成，颜色操作最多两个

规则：一张普通采样纹理，后面串联不超过两个一元颜色操作（色彩矩阵 ColorMatrix、亮度 Luma、透明度阈值 AlphaThreshold、色彩空间转换 ColorSpaceXform），整体由一个预编译程序单 Pass 完成；第三个颜色操作出现即超出容量[^4]。

```cpp
// 命中：1 张纹理 + 2 个颜色操作，恰好达到容量上限。
Paint paint;
paint.setShader(Shader::MakeImageShader(image, TileMode::Clamp, TileMode::Clamp));
paint.setColorFilter(ColorFilter::Compose(ColorFilter::Luma(), ColorFilter::Matrix(matrix)));
canvas->drawRect(rect, paint);
```

数据流：`纹理采样 → 色彩矩阵 → 亮度 → 输出`，全程寄存器传值，无中间纹理。

可以这样做：超过两个操作时，先把多个 ColorMatrix 在 CPU 侧合并成单个矩阵（矩阵乘法即可）；无法合并的，把稳定的前缀效果离线烘焙成一张纹理，运行时只保留链尾操作。

### 3.2 带分支的颜色关系在单 Pass 内求值，上限为十六条操作记录与四个真实纹理源

规则：两个颜色源之间的混合（Blend）、常量颜色参与的颜色运算，与第 3.1 节的一元操作可以组成带分支的颜色关系图，由一个预编译程序在单 Pass 内求值，不需要中间纹理[^1][^3]。

```cpp
// 命中：2 张纹理 + 1 个混合 + 1 个色彩矩阵 = 4 条操作记录，远在 16 条上限内。
Paint paint;
auto dst = Shader::MakeImageShader(backgroundImage, TileMode::Clamp, TileMode::Clamp);
auto src = Shader::MakeImageShader(foregroundImage, TileMode::Clamp, TileMode::Clamp);
paint.setShader(Shader::MakeBlend(BlendMode::Multiply, dst, src));
paint.setColorFilter(ColorFilter::Matrix(saturationMatrix));
canvas->drawRect(rect, paint);
```

容量与约束，每条都可独立判定：

- 操作记录总数不超过 16 条；每条记录是一个一元操作、一次纹理采样、一个常量颜色或一次两源混合[^1]。
- 真实纹理源不超过 4 个；第 5 个纹理源出现即整体未命中[^2]。
- 非空的颜色关系图固定绑定 4 个纹理采样器，真实纹理不足 4 个时由库用第一个纹理补齐空位，接入方无需处理[^3]。
- 色彩空间转换每图最多出现一次；渐变色源最多一个；抗锯齿矩形覆盖最多一个；使用查找表的渐变最多与一个纹理源共存[^6]。
- 参与图的纹理必须是普通采样或瓦片采样；YUV 纹理、带透视的采样、设备空间采样一律拒绝；同一张纹理不能同时是仅透明度格式又携带 RGBAAA 附加位[^5]。

可以这样做：纹理源超过 4 个时，把其中稳定的两层预先合成到一张离屏纹理再参与绘制；操作记录超限时，优先合并相邻 ColorMatrix，其次把不随帧变化的分支烘焙成纹理。

### 3.3 纹理填充的编译期接口只有少量开关，其余差异全部是运行时参数

规则：最基础的"画一张图"路径，其程序变体只由少数几个编译期开关张成；纹理格式、混合模式取值、坐标矩阵等差异通过参数上传，不产生新变体。

编译期开关（以纹理填充为例）：

- `HAS_XP`：本次绘制与目标表面的混合方式，3 个取值——无附加混合、Porter-Duff 混合（双源实现）、Porter-Duff 混合（读取帧缓冲实现）。
- `HAS_DEVICE_MASK`：是否叠加一层设备空间遮罩纹理。
- 四边形变体额外有 `HAS_SUBSET`（采样子区域）与 `HAS_LOCAL_MASK`。

运行时参数（不张成变体）：纹理是仅透明度格式（AlphaOnly）、纹理携带 RGBAAA 附加位（HasRGBAAA）、采样矩阵、子区域坐标。

```cpp
// 命中：纯绘制，开关由库按绘制特征自动选择，接入方无感知。
canvas->drawImage(image, &paint);
```

可以这样做：接入方不需要为这些开关做任何事；需要控制包体时，只需知道每多一个开关维度，条目数按取值数相乘，这是第 8 节条目数的来源。

### 3.4 文本、渐变、噪声、YUV 等高频形状拥有专用 Shader，不经分解直接命中

规则：以下形状各有独立的预编译专用程序，参数以运行时上传为主，命中与否不经过第 3.1/3.2 节的分解判定[^8]。

| 形状 | 典型调用 | 说明 |
| --- | --- | --- |
| 图集文本 | `canvas->drawTextBlob(...)` | 字形从图集纹理读取，覆盖叶在片元阶段注入。 |
| 解析渐变 | `Shader::MakeLinearGradient` / `MakeRadialGradient` / `MakeConicGradient` / `MakeDiamondGradient` | 渐变颜色由坐标解析计算，查找表形式也在支持范围内。 |
| Perlin 噪声 | `Shader::MakeFractalNoise` / `MakeTurbulence` | 噪声源之后允许再串联最多三个一元颜色操作[^4]。 |
| YUV 纹理填充 | 直接绘制视频帧图像 | 按 YUV 格式维度张成变体，与第 4.3 节的"链内拒绝 YUV"互补。 |
| 单向高斯模糊 | 参数受契约约束的模糊路径 | 独立的预编译契约，不代表任意模糊可分解，见第 4.2 节。 |

可以这样做：构造效果时优先落在这些专用形状上——能用渐变 Shader 就不用渐变贴图，能直接绘制 YUV 帧就不要先转 RGBA 再进颜色链。

## 4. 不支持的结构都有明确的识别特征，且各自有标准替代做法

### 4.1 需要读取目标颜色的自定义混合不受支持

规则：绘制结果与帧缓冲已有内容的最终混合，超出 Porter-Duff 集合时需要自定义混合逻辑，预编译程序不携带此类混合器。

```cpp
// 未命中：ColorDodge 不属于 Porter-Duff 集合。
paint.setBlendMode(BlendMode::ColorDodge);
canvas->drawImage(image, &paint);
```

注意与第 3.2 节的区分：第 3.2 节支持的是两个颜色源之间的混合（`Shader::MakeBlend`），发生在绘制内部；本节限制的是绘制结果与目标表面的混合。前者由融合 Shader 计算，后者由管线混合阶段执行。

可以这样做：改用 Porter-Duff 集合内的混合模式（SrcOver、SrcIn、DstOut 等）；或先把前景画到一张离屏纹理，再以 Porter-Duff 模式合成到目标表面。

### 4.2 邻居采样效果不受支持：模糊、卷积、阴影、马赛克

规则：凡输出像素依赖邻域输入像素的效果，一律不在可分解子集内[^8]。

```cpp
// 未命中：高斯模糊是邻域效果。
paint.setImageFilter(ImageFilter::Blur(8, 8));
canvas->drawImage(image, &paint);
```

可以这样做：参数受契约约束的高斯模糊走独立的专用预编译路径（第 3.4 节）；`DropShadow` 等复合效果改在应用层拆成"阴影层 + 内容层"两次绘制；马赛克类效果用"先缩小到离屏纹理、再最近邻放大"的两步绘制手工实现，每步各自落在子集内。

### 4.3 YUV、透视、RGBAAA 纹理不进入普通颜色链

规则：颜色链内的纹理叶只接受普通采样或瓦片采样的 RGBA/仅透明度纹理；YUV 纹理、带透视矩阵的采样、AlphaOnly 与 RGBAAA 同时成立的纹理，在链内一律拒绝[^5]。

```cpp
// 未命中：带透视的图像绘制不进颜色链。
canvas->concat(Matrix::MakePerspective(...));
canvas->drawImage(image, &paint);
```

可以这样做：YUV 帧直接绘制，走第 3.4 节的 YUV 专用路径，不要先套颜色滤镜；需要透视时先光栅化到无透视的中间纹理，再对中间纹理应用颜色链；RGBAAA 纹理由库在专用填充路径处理，不要手动拼进多纹理颜色关系图。

### 4.4 任意 RuntimeEffect 不受支持

规则：`RuntimeEffect` 携带接入方自定义的 Shader 源码，构建期无法枚举其形态，任何包含它的组合整体未命中，且不存在"部分命中"。

```cpp
// 未命中：自定义源码无法预编译。
auto effect = RuntimeEffect::MakeForShader(customSource);
paint.setShader(effect->makeShader(...));
canvas->drawRect(rect, paint);
```

可以这样做：逐项检查自定义源码的语义——能表示为色彩矩阵、亮度、阈值、两源混合的，改写为对应的枚举内操作；无法改写的，在构建自己的资源管线时离线执行该效果并烘焙成纹理。

### 4.5 复杂遮罩与不可折叠的覆盖率不受支持

规则：覆盖率必须能折叠成"对颜色做一次乘法"；多层嵌套裁剪与遮罩叠加后无法用单次乘法表达时，该绘制不进子集。

```cpp
// 未命中：裁剪、遮罩、模糊遮罩三层叠加的覆盖率无法折叠。
canvas->clipPath(complexPath);
paint.setMaskFilter(maskFilter);
paint.setImageFilter(ImageFilter::Blur(4, 4));
canvas->drawImage(image, &paint);
```

可以这样做：把多层裁剪合并成单层路径；把复杂遮罩预渲染成一张设备空间遮罩纹理——单层设备遮罩是纹理填充路径的标准开关（`HAS_DEVICE_MASK`），在子集内。

### 4.6 任意递归依赖图不能自动变成多 Pass 序列

规则：分解只产出单 Pass 结果；需要多个中间纹理依次传递的深层滤镜序列，库不会自动为其规划 Pass 序列与中间纹理分配。

```cpp
// 未命中：模糊-调色-再模糊需要两次中间纹理，不自动拆 Pass。
auto filter = ImageFilter::Compose(
    ImageFilter::Blur(4, 4),
    ImageFilter::Compose(ImageFilter::ColorFilter(colorFilter), ImageFilter::Blur(4, 4)));
paint.setImageFilter(filter);
canvas->drawImage(image, &paint);
```

可以这样做：在应用层用多个 Surface 显式拆分，每个 Pass 的效果分别落在子集内；中间纹理的尺寸、格式、生命周期由应用层控制，GPU 成本也因此可预测。

### 4.7 需要高精度中间结果的链路不拆 Pass

规则：拆 Pass 意味着中间结果写入 RGBA8 纹理，8 位量化不可接受的链路不允许拆分；这类链路只有两种结局——整体融合进单 Pass（受容量限制），或保持运行时编译。

- 例：两个 ColorMatrix 之间要求 16 位浮点精度的高动态范围调色，若拆成两个 Pass，中间纹理会把中间值量化到 8 位，产生可见色带。

可以这样做：把精度敏感的操作合并到同一个 Pass 内（第 3.1/3.2 节的容量内融合不损失精度）；确认超出容量时，显式接受该绘制的运行时编译成本，不要用拆分换命中率。

## 5. 确认组合是否受支持有三层手段：构建期报告、运行时诊断、静态检查接口

### 5.1 构建期报告给出子集的全量清单与体积账目

每次生成 Bundle 都会产出构建报告：各后端的条目数、体积、逐 Shader 的分解，以及一份结构审计——校验预编译清单与库内路由规则严格一致，不多编译也不少编译[^9]。着色相关的源码改动后必须重新生成并发布 Bundle，报告随之更新[^10]。

用法：把构建报告纳入版本库评审，条目数与体积的每一次变化都能对应到具体的功能改动；接入方升级库版本时，对比两份报告即可知道子集边界移动了什么。

### 5.2 运行时诊断给出命中率、Pass 数与降级原因

库内部维护逐次绘制的命中统计：某次绘制由预编译程序服务（命中）还是走了运行时编译（未命中）、未命中时的降级原因分类、以及一次绘制实际执行的 Pass 数。当前这些计数通过测试工程与内部分析工具暴露，用于持续追踪真实负载的命中率，尚未以公开 API 形式提供。

用法：在集成测试里接入诊断计数，为关键页面设定命中率基线；任何一次改动引入新的未命中族，诊断会按降级原因聚类，直接指向第 4 节中的某一类。

### 5.3 静态检查接口是建议方向，当前不存在

建议在 Context 上提供查询接口：输入一次绘制的完整参数描述（Shader 种类、颜色滤镜序列、混合模式、纹理格式），输出"能否由预编译程序服务"及原因码。该接口把第 3、4 节的规则从文档变成可执行判定，供接入方在资源制作管线里离线筛查素材。当前版本没有此接口，接入方以第 5.1 节的清单比对加第 5.2 节的运行数据间接确认。

## 6. 四个后端的预编译资产形态不同，OpenGL 的最终编译仍在驱动内完成

| 后端 | 资产形态 | 条目数 | Bundle 体积 | 运行时残留的编译行为 |
| --- | --- | --- | --- | --- |
| Metal | 预编译 metallib 二进制 | 375 | 1.14 MB | 无，驱动直接加载 |
| Vulkan | SPIR-V 二进制 | 375 | 1.77 MB | 无驱动编译，管线创建仍有固定成本 |
| OpenGL | GLSL 源码 | 375 | 153 KB | 驱动在运行时完成最终编译与链接，包体最小但运行时成本未消除 |
| WebGPU | WGSL 源码 | 283 | 545 KB | 运行时经 tint 转译为底层着色语言，转译成本显著低于全量 JIT |

三点结论：

- 条目数 375 与 283 的差异来自各后端独立的可编译清单；WebGPU 清单剔除了该后端无法通过验证的组合，属于刻意收窄而非缺失。
- OpenGL 的"预编译"只做到源码级预生成与变体枚举，驱动编译与链接无法前置；评估 OpenGL 的启动成本时不能引用 Metal/Vulkan 的数据。
- 体积差异主要来自资产形态：二进制后端为每条目携带完整编译产物，源码后端只携带文本；包体大小不代表运行时成本高低。

## 7. 能力扩展按固定顺序推进，每一步都不动摇已有子集

1. 先补低成本静态变体：在不改变资源绑定方式的前提下，为已有专用 Shader 增补参数组合。例：为某条专用填充路径补一种采样模式组合，包体只增加少量条目，即可消除一整类未命中。这一步不改变任何规则，只扩大枚举。
2. 再扩展受支持的节点类型：把新的逐像素操作加入枚举，并同步更新全部四个后端的资产与审计。例：新增一种一元颜色操作时，第 3.2 节的操作记录语义不变，容量上限不变，只是可选操作多了一种。
3. 再考虑中间结果格式升级：把中间纹理从 RGBA8 升级到更高精度格式，解除第 4.7 节的限制。代价是中间纹理的显存与带宽成倍上升，需要配合格式协商机制。
4. 最后才考虑更复杂的依赖图：为深层滤镜序列自动规划多 Pass。代价是每帧的中间纹理分配与 GPU 成本从静态可预测变为动态可变，只有在前三步的收益耗尽后才值得启动。

## 8. 附录：包体数据证实接入方实际增量只有 Bundle 量级

| 资产 | 数据 | 说明 |
| --- | --- | --- |
| Metal Bundle | 1.14 MB，375 条目 | 预编译 metallib，随库分发 |
| Vulkan Bundle | 1.77 MB，375 条目 | SPIR-V，随库分发 |
| OpenGL Bundle | 153 KB，375 条目 | GLSL 源码，随库分发 |
| WebGPU Bundle | 545 KB，283 条目 | WGSL 源码，随库分发 |
| libshader-tool-vendor.a | 约 19 MB/后端 | 构建期着色工具链静态库，只在构建机使用，不进入发布包 |
| tgfx.a | 依构建配置约 418 / 423 / 398 MB | 含全部内嵌资产与调试信息的主静态库；发布裁剪后的包体增量以 Bundle 行为准 |

包体结论：接入方实际承担的增量是 Bundle 行（合计约 4 MB 量级，按接入的后端选取）；构建工具链与主静态库的体积只影响构建机与开发包，不影响终端用户。
